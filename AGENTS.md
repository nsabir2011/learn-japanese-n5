# Repository guidance

## Changelog and releases

The in-app update banner and changelog are driven by `content/releases.json`.

- Add one release entry for each publishable batch that contains user-visible behavior, content, or design changes.
- Do not create a release for tests, refactors, documentation, build tooling, or other internal-only changes.
- Append releases in publication order. Never edit, remove, or reorder an entry that has already been published.
- Format release IDs as `YYYY-MM-DD.N`, incrementing `N` for additional releases on the same date.
- Group related work into one release entry instead of creating an entry per commit.
- Write brief user-facing titles and change descriptions. Avoid file names, implementation details, and developer jargon.
- Use the narrowest applicable page scope: `home`, `hiragana`, `katakana`, `kana`, `vocabulary`, `numbers`, `settings`, or `guided`.
- Use `all` only when the change benefits every page. A release may contain several changes with different scopes.
- Describe changes across the whole app, not only the page used while developing or testing.
- Edit only the source manifest. `public/trainer` is generated by `npm run prepare:site` and must not be edited directly.
- Before publishing, run `npm test` and `npm run build` and fix any failures.
